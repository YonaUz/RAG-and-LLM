Generative modelling allows us to provide data that is similar to and inspired from existing data. In RAG and LLM, the existing data are texts. But text data nowadays exist under multiple forms, and file types (pdf, websites, code files like html, css, Python, Javascript...), and across thousands of subjects. The subject here chosen is Remote Sensing, and more particularly Sentinel 2 and Landsat 8 and 9 satellites. _Why this subject ?_ For many reasons, firstly to get started with one interesting subject, secondly because I started learning about them at work, and because it reveals traps and tricky questions to think about. 
Ready to start ? Welcome to the adventure! 

Generative modelling is based on observation: in language models, one observation may be that some words are usually associated to another; "Queen" goes to "She" while "King" goes to "He"; "The cat eats the mouse" or "The mouse is eaten by the cat", but rarely inverse. In image modelling, cars are located in the street and the sea is blue, while rarely pedestrians smile under the rain...  And so on the generated image will be, based on the probabilistic observed text or image.

#### I. Loading the documents to build up the knowledge base
0. First start with `00_framing_and_fundamentals.ipynb` which details the subject and scope of the project. We will deal with Sentinel 2, Landsat 8 and 9 satellites, and read/ learn about Satellite missions, Sensors, Spectral bands, Spatial resolution, Spectral resolution, Temporal resolution, Spectral indices, Remote sensing applications, Data products and Processing methods.

1. Notebook `01_document_ingestion.ipynb` defines and creates the folders needed for the project, distinguishing the raw documents from the processed files. The raw docs are Sentinel 2 and Landsat 8 and 9 data sheets. We use Langchain framework to load the files with PyPDFLoader library for PDF files. It allows reading the file, preview it and extract metadata. The processed files are those files stored in a JSONL file. To avoid having to reread and reload all the PDFs at each execution, we save the ingestion result in JSONL format in the processed subfolder. JSONL means JSON Lines: each line is an independent JSON object and contains a page loaded text with its metadata.

2. In the second notebook `02_document_splitting.ipynb`, we retrieve the ingested jsonl file and split the text into chunks. Ideally, documents are split into chunks that contain sufficient context to be useful to the LLM. However, larger doesn't always mean better. If the chunks are huge, retrieval will be slow, and the LLM may struggle to extract the most relevant context from the chunk to respond to the query. The chunk_size parameter is used to control this balance. Another parameter, chunk_overlap, is used to capture important information that may be lost around the boundaries between chunks. In this notebook, we consider 3 different splitting or chunking methods. 
For the first method, we instantiate the `RecursiveCharacterTextSplitter` splitter from `langchain_text_splitters`. We specify the separator to split on ("\n\n", "\n", " ", ""`); in our case, it will split the text with each new paragraph, with chunk_size below 1000 and 150 overlapping characters. 
The second method to be considered is the token based splitting. Instead of splitting over character, we split on token. The `RecursiveCharacterTextSplitter` has a few limitations. The resulting splits are effectively "naive" because they are executed without considering the context of the surrounding text.This means related information will potentially be stored and processed separately, which will lower the quality of our RAG application. We recall that the language models we're using, break text into tokens, or smaller units of text, for processing. If we split documents using characters rather than tokens, we risk retrieving chunks and creating a retrieval prompt that exceeds the maximum amount of text the model can process at once, also called the model context window.Using token splitter, we make the model more aware of the document's context and enable splitting with tokens.
Then, `TokenTextSplitter` requires the name of the encoding to use ("gpt-4o-mini"), which is the encoding used by the large language model and can be retrieved using the tiktoken. This encoding can check the number of tokens in each chunk. 
The third method considered tries to overcome a common drawbacks of the previous splitting methods. The split doesn't consider the context of the surrounding text, so context can easily be lost during splitting. The semantic text splitter `SemanticChunker` is a cutting-edge experimental method for splitting text based on semantic meaning. When the splitter detects that the meaning of the text has deviated past a certain threshold, a split will be performed. The semantic text splitter uses vector gradients to determine semantic similarity and uses 0.8 as the threshold at which to split. This  threshold is set to identify significant changes in distance. When the change in semantic distance exceeds this threshold, it indicates a potential topic shift.
Finally, we save the splitted document with the recursive character splitter method to be able to reload it later.
